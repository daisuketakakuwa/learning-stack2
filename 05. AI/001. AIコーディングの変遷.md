# AIコーディングの変遷

## 一言でまとめると
- Prompt Engineering：AIへの「指示（プロンプト）自体」をどう組み立てるか
- Context Engineering：AIがタスクを遂行するために「何の情報を、いつ、どこから参照すべきか」を設計する。例えば コンテキストマップ.md を用意して「まずここを見る → 必要なら次にここを見る」と案内することも、その一つ
- Harness Engineering：AIにソフトウェア開発をさせるために、コード、ドキュメント、Git、Terminal、テスト、各種Tools、SandboxなどをAIが適切に参照・操作でき、開発作業を最後まで進められるように環境・仕組み全体を整備すること
- ACI Engineering：Harnessの中でも特に、AIがFilesystem、Terminal、Git、BrowserなどのComputer機能を「どう操作するか」というAIとComputerの接点（Interface）を設計すること

ざっくり言えば、
```
Prompt Engineering
「AIにどう指示する？」
        ↓
Context Engineering
「AIに何を見せる？ どこを見に行かせる？」
        ↓
ACI Engineering
「AIにどんな手足・操作手段を与える？」
        ↓
Harness Engineering
「それら全部を組み合わせて、
 AIが実際に開発を遂行できる環境をどう作る？」
```

つまり、AIコーディングの発展は、

> 「良い指示を書く」から、「必要な情報へ導く」、さらに「AI自身がツールを使いながら開発を遂行できる環境を作る」へと、設計対象が広がってきた

と捉えると分かりやすい。


## はじめに

AIによるコーディング／ソフトウェアエンジニアリングを理解するうえで、重要な概念の流れとして次の3つがある。

```text
Prompt Engineering
        ↓
Context Engineering
        ↓
Harness / ACI Engineering
```

これは単純に「古い技術から新しい技術へ置き換わった」という意味ではない。

むしろ、

> **AIをうまく働かせるために、人間が設計する対象が徐々に広がってきた**

と捉えると理解しやすい。

大まかには次のように対応する。

| 概念                  | 主に設計するもの              |
| ------------------- | --------------------- |
| Prompt Engineering  | AIに「何をどう頼むか」          |
| Context Engineering | AIに「何を知った状態で考えさせるか」   |
| ACI Engineering     | AIに「コンピュータをどう操作させるか」  |
| Harness Engineering | AIに「どうやって仕事全体を遂行させるか」 |

---

# 1. Prompt Engineering

## Promptとは何か

Prompt Engineeringは、

> **LLMに入力する指示をどのように設計するか**

という考え方である。

例えば、

```text
PythonでTODOアプリを作って
```

と指示するより、

```text
FastAPIを使ってREST APIを実装してください。

条件:
- Python 3.12
- 型ヒント必須
- SQLiteを使用
- pytestでテストを作成
- 実装前に設計方針を説明する
```

とした方が、求めている出力を得やすい。

基本構造は非常にシンプルである。

```text
Human
  │
  │ Prompt
  ▼
 LLM
  │
  ▼
Output
```

つまりPrompt Engineeringでは、

> **Prompt → Output**

という変換をうまく制御することが中心となる。

---

# 2. Promptだけでは足りない

AI Codingが高度になると、Promptの工夫だけでは解決できない問題が出てくる。

例えば、

```text
このプロジェクトにログイン機能を追加して
```

と依頼したとする。

この仕事をするには、AIは少なくとも次のような情報を知る必要がある。

```text
どんなファイルが存在するのか？

どのFrameworkを使っているのか？

既存の認証処理はどうなっているのか？

DB Schemaは？

Coding Conventionは？

既存テストは？

過去にどんな設計判断をしたのか？
```

Promptがどれだけ上手でも、必要な情報そのものがAIに与えられていなければ仕事はできない。

そこで重要になるのが **Context Engineering** である。

---

# 3. Context Engineering

## Contextとは何か

LLMはPromptだけを見ているわけではない。

実際には、さまざまな情報がContext Windowに入った状態で推論を行う。

```text
┌──────────────────────────────┐
│        Context Window        │
│                              │
│ System Instructions          │
│ User Prompt                  │
│ Repository Files             │
│ Documentation                │
│ Previous Conversation        │
│ Tool Results                 │
│ Error Messages               │
│ Test Results                 │
│ Git Diff                     │
│ etc...                       │
└──────────────┬───────────────┘
               │
               ▼
              LLM
```

Context Engineeringとは、

> **AIが仕事をするとき、何を知っている状態にするかを設計すること**

と考えることができる。

---

## Repository全体を渡せばいいわけではない

例えば100万行あるRepositoryをAIに扱わせるとする。

毎回すべてのコードをLLMに渡すのは現実的ではない。

そこで、

```text
User
「ログイン機能を修正して」
        │
        ▼
Repository Search
        │
        ▼
関連ファイルを発見

auth/
├── login.ts
├── session.ts
└── middleware.ts

        │
        ▼
必要なファイルをContextへ
        │
        ▼
       LLM
```

という処理を行う。

Contextとして利用できるものには例えば、

```text
README
architecture.md
AGENTS.md
Repository内のコード
Git history
関連テスト
Error log
Tool execution result
過去の会話
Memory
```

などがある。

重要なのは、

> **大量の情報を渡すこと**

ではなく、

> **必要な情報を、必要なタイミングで、適切な形で渡すこと**

である。

---

# 4. AIが「回答する」から「行動する」へ

PromptとContextが揃っていても、まだAI自身がコンピュータを操作できるとは限らない。

例えばAIに、

```text
このRepositoryのBugを直して
```

と頼んでも、

```text
ファイルを読めない
コード検索できない
ファイルを書き換えられない
Terminalを使えない
Testを実行できない
Git diffを確認できない
```

という状態では、本当の意味でBug修正を完遂することは難しい。

そこでAIに **Tools** を与える。

例えば、

```text
read_file(path)

edit_file(path, patch)

search_code(query)

run_command(command)

run_tests(target)

git_diff()
```

などである。

するとAIは単に文章を出力するだけではなく、

```text
コードを読む
↓
考える
↓
コードを書き換える
↓
Testする
↓
Errorを見る
↓
再び修正する
```

という「行動」が可能になる。

---

# 5. Agent Loop

ここで重要になるのが **Agent Loop** である。

Coding Agentは一度LLMを呼び出して終わるとは限らない。

例えば、

```text
問題を理解する
      ↓
コードを検索する
      ↓
関連ファイルを読む
      ↓
修正する
      ↓
Testを実行する
      ↓
Test failed
      ↓
Error logを読む
      ↓
原因を考える
      ↓
再修正
      ↓
Test
      ↓
Pass
      ↓
Git diff確認
      ↓
完了
```

というループを回す。

抽象化すると、

```text
Observe
   ↓
Decide
   ↓
Act
   ↓
Observe
   ↓
Decide
   ↓
Act
   ↓
...
```

となる。

簡略化した疑似コードなら、

```python
while True:
    response = llm(
        messages,
        tools=[
            read_file,
            edit_file,
            run_shell,
        ],
    )

    if response.finished:
        break

    result = execute(response.tool_call)

    messages.append(result)
```

程度でも、Agent Loopの原型になる。

LLMが、

```text
次に何をするべきか？
```

を判断し、

Harness側が、

```text
その行動を実際に実行する
```

という関係になっている。

---

# 6. ACI Engineering

ACIは **Agent-Computer Interface** の略として使われる。

これはHCI（Human-Computer Interaction）と比較すると理解しやすい。

```text
HCI

Human
  ↕
Computer
```

に対して、

```text
ACI

AI Agent
   ↕
Computer
```

である。

つまりACI Engineeringとは、

> **AI Agentにとって使いやすいコンピュータとの接点をどう設計するか**

という問題である。

---

## 人間向けUIとAI向けUIは違う

人間は、

```text
Mouse
Keyboard
GUI
Button
Menu
IDE
```

などを使ってComputerを操作する。

しかし、AI AgentにとってGUIが最適とは限らない。

AIには例えば、

```text
read_file(path)

write_file(path, content)

edit_file(path, patch)

search_code(query)

run_tests(target)

run_command(command)

git_diff()
```

のようなInterfaceの方が扱いやすい場合がある。

つまり、

```text
AI Agent
    │
    ▼
┌─────────────────┐
│       ACI       │
│                 │
│ read_file       │
│ edit_file       │
│ search_code     │
│ shell           │
│ git             │
│ browser         │
└────────┬────────┘
         │
         ▼
     Computer
```

という構造である。

ACIはAIにとっての、

> **手・目・操作盤**

のようなものと考えると分かりやすい。

---

# 7. Harness Engineering

ここからさらに視野を広げる。

Harnessとは、

> **LLMを実際にAgentとして働かせるため、その周囲に構築されたソフトウェア・実行環境・制御ロジックの総体**

と考えると理解しやすい。

重要なのは、

> **Harnessという単一のファイルや特定のツールが存在するわけではない**

という点である。

Promptの場合は、

```text
「この文字列がPromptです」
```

と言える。

一方Harnessの場合、

```text
「これ1個がHarnessです」
```

という単一の実体があるとは限らない。

複数のプログラム、設定、Tool、Runtimeなどが組み合わさってHarnessを形成する。

---

# 8. Harnessの「実物」

例えば自分でCoding Agentを作ったとする。

Repositoryが次のようになっているかもしれない。

```text
my-coding-agent/
│
├── agent.py
│   └── Agent Loop
│
├── prompts/
│   └── system.md
│
├── tools/
│   ├── read_file.py
│   ├── edit_file.py
│   ├── grep.py
│   └── shell.py
│
├── context/
│   ├── selector.py
│   └── compactor.py
│
├── sandbox/
│   └── runtime.py
│
├── git/
│   └── diff.py
│
└── config.yaml
    └── Permissions / Limits
```

この場合、

> **このシステム全体がCoding Harness**

と考えることができる。

---

# 9. Harnessの構成要素

Harnessには例えば次のようなものが含まれうる。

```text
Tools

Agent Loop

Context Management

Memory

Repository Search

Filesystem Access

Terminal

Git

Test Runner

Compiler

Browser

Sandbox

Permissions

Timeout

Retry

Validation

Logging / Observability

Error Recovery
```

したがって、

```text
Tools
Agent loop
Sandbox
Tests
Git
Terminal
Memory
```

はすべて **Harnessの構成要素になりうる**。

ただし、

> GitそのものがHarness
> TerminalそのものがHarness

という意味ではない。

それらを **AI Agentが利用できるように接続・制御する仕組み** がHarnessの一部となる。

---

# 10. Gitを例に考える

普通のGitは単なる開発ツールである。

しかしCoding AgentがGitを利用する場合、

```text
LLM

「現在の変更点を確認したい」
        │
        ▼
Harness
        │
        ▼
git_diff Tool
        │
        ▼
git diff
        │
        ▼
実行結果
        │
        ▼
必要なら結果を加工・圧縮
        │
        ▼
Contextへ追加
        │
        ▼
LLM
```

という仕組みになる。

このときGitはHarnessの中に組み込まれた能力の一つになる。

同じことが、

```text
Terminal
Filesystem
Browser
Compiler
Test Runner
```

などにも言える。

---

# 11. Harness全体像

Coding Harnessを概念的に描くと次のようになる。

```text
                 ┌───────────┐
                 │    LLM    │
                 └─────┬─────┘
                       │
                       ▼
                 ┌───────────┐
                 │Agent Loop │
                 └─────┬─────┘
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
        Tools        Context      Control
          │            │            │
     read_file     repo search   permissions
     edit_file     source code   sandbox
     shell         AGENTS.md     timeout
     search        git history   retries
     git           tool result   validation
     tests         memory        error recovery
          │            │            │
          └────────────┼────────────┘
                       │
                       ▼
                  Real Computer
```

この「LLMを取り囲む仕組み」がHarnessである。

---

# 12. ACIとHarnessの違い

ACIとHarnessはかなり重なるが、同じものではない。

ACIは特に、

> **AgentとComputerの接点**

に注目する。

```text
Agent
  │
  ▼
 ACI
  │
  ├── read_file
  ├── edit_file
  ├── search
  ├── shell
  ├── git
  └── browser
  │
  ▼
Computer
```

Harnessはさらに広い。

```text
Harness
│
├── Agent Loop
├── Context Management
├── Memory
├── Permissions
├── Sandbox
├── Validation
├── Error Recovery
├── Logging
│
└── ACI
    ├── read_file
    ├── edit_file
    ├── search
    ├── shell
    ├── git
    └── browser
```

覚え方としては、

> **ACI = AIの「手足・操作盤」を設計する**

> **Harness = その手足も含めて「AIを働かせる機械全体」を設計する**

とすると分かりやすい。

---

# 13. Prompt / Context / ACI / Harnessの「実物」の違い

| 概念                  | 一言で言うと            | 実物として見ると                                                  |
| ------------------- | ----------------- | --------------------------------------------------------- |
| Prompt Engineering  | 何をどう頼むか           | LLMに渡すInstructionなどの文字列・Message                           |
| Context Engineering | 何を知った状態にするか       | Files、Docs、History、Tool Resultなどと、それを選択・構成するロジック          |
| ACI Engineering     | どうComputerを操作させるか | Tool / API / Interface                                    |
| Harness Engineering | どう仕事全体を遂行させるか     | LLM、Context、Tools、Runtime、Agent Loop、Sandboxなどを統合した周辺システム |

この中では **Harnessが最もシステム全体寄りの概念** である。

---

# 14. 3つは入れ子として考えられる

大雑把には次のような構造として理解できる。

```text
┌─────────────────────────────────────────┐
│           Harness Engineering           │
│                                         │
│  Agent Loop / Tools / Sandbox / Git     │
│  Tests / Permissions / Validation       │
│                                         │
│    ┌───────────────────────────────┐    │
│    │      Context Engineering      │    │
│    │                               │    │
│    │ Files / Docs / History        │    │
│    │ Errors / Tool Results         │    │
│    │                               │    │
│    │    ┌────────────────────┐     │    │
│    │    │Prompt Engineering  │     │    │
│    │    │                    │     │    │
│    │    │ Instructions       │     │    │
│    │    └────────────────────┘     │    │
│    └───────────────────────────────┘    │
│                                         │
└─────────────────────────────────────────┘
```

完全に厳密な包含関係というより、

> **AIを制御する対象が外側へ広がっていく**

イメージとして捉えるとよい。

# 15. AI Codingの変遷

初期のAI Codingは、

```text
Human
  │
  │ Prompt
  ▼
 LLM
  │
  ▼
Code
```

という形が中心だった。

ここでは、

> 「どう質問すれば良いコードを書いてくれるか？」

が重要だった。

つまり **Prompt Engineering中心** である。

---

その後、

```text
             Context
               │
               ▼
Human ───────▶ LLM
               │
               ▼
              Code
```

となる。

Repository、Documentation、過去の会話などを適切に与える必要が出てきた。

つまり、

> 「どう質問するか？」

だけではなく、

> 「何を見せた状態で考えさせるか？」

が重要になった。

これが **Context Engineering** である。

---

さらにCoding Agentでは、

```text
              LLM
               │
               ▼
           Agent Loop
               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
   Files     Terminal    Git
     │         │         │
     └─────────┼─────────┘
               ▼
             Tests
               │
               ▼
          Feedback
               │
               └──────▶ LLM
```

となる。

AIはコードを「生成する」だけではなく、

```text
読む
↓
検索する
↓
編集する
↓
実行する
↓
失敗する
↓
原因を調べる
↓
修正する
↓
検証する
```

ようになる。

ここで **Harness / ACI Engineering** が重要になる。

# 16. 本質的な変化

AI Codingの変化を一言で表すなら、

```text
「AIにコードを書かせる」
          ↓
「AIに開発作業をさせる」
```

という変化である。

前者では、

```text
Prompt → Code
```

が中心になる。

後者では、

```text
LLM
 +
Context
 +
Tools
 +
Agent Loop
 +
Environment
 +
Feedback
 +
Guardrails
```

というシステム全体が必要になる。

つまり、

```text
LLM
 + Context
 + Tools
 + Agent Loop
 + Environment
 + Feedback
 + Guardrails

             ↓

        Coding Agent
```

と考えることができる。

# 17. Harness Engineeringが重要になる理由

モデル自体が非常に賢くても、

```text
Repositoryを読めない

Searchできない

Fileを書き換えられない

Terminalを使えない

Testできない

Errorを確認できない
```

なら、実際のSoftware Engineering能力には大きな制約がある。

逆に、

```text
Strong LLM
     +
Repository Access
     +
Search
     +
Editor
     +
Terminal
     +
Compiler
     +
Tests
     +
Git
     +
Browser
     +
Memory
     +
Agent Loop
```

を組み合わせると、

```text
Issue理解
↓
Repository調査
↓
原因特定
↓
実装
↓
Test
↓
失敗
↓
Error解析
↓
修正
↓
再Test
↓
Diff確認
↓
完了
```

というSoftware Engineeringの一連の流れを実行できる。

したがって、AI Codingでは、

> **モデル単体の知能**

だけでなく、

> **モデルを取り囲む環境をどれだけ上手く設計できているか**

も非常に重要になる。

これがHarness Engineeringを理解するポイントである。

# 18. 用語についての注意

`Harness Engineering` や `ACI Engineering` は、すべての人が完全に同じ意味・境界で使用している用語とは限らない。

特にHarnessは文脈によって、

```text
Agent Runtimeを中心に指す場合

Tool executionまで含める場合

Context managementまで含める場合

SandboxやPermissionsまで含める場合

Evaluation / Observabilityまで広く含める場合
```

などがある。

したがって、

> **Harnessという特定の製品・技術・ファイル形式が存在する**

と考えるのではなく、

> **LLM/Agentを実際に働かせるための周辺システム**

という概念として捉えるのがよい。

# 20. 最終的な理解

AI Codingを理解するうえで、最初に持っておきたいモデルは次の通り。

```text
Prompt Engineering
=
AIへの「指示」を設計する


Context Engineering
=
AIの「知っている状態」を設計する


ACI Engineering
=
AIの「手足・操作盤」を設計する


Harness Engineering
=
AIがそれらを使って
「仕事を遂行できる環境全体」を設計する
```

そしてAI Codingの大きな流れは、

```text
Prompt
「どう頼むか？」
        ↓
Context
「何を知った状態にするか？」
        ↓
Tools / ACI
「何を操作できるようにするか？」
        ↓
Harness
「どうすれば仕事全体を完遂できるか？」
```

と捉えることができる。

最終的には、

```text
AI Coding
≠
LLMにコードを書かせるだけ

AI Coding
=
LLMをSoftware Engineering Systemの
一部として機能させる
```

という理解につながる。
