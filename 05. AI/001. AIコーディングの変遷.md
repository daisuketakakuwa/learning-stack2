# AIコーディングの変遷

## 一言でまとめると
- Prompt Engineering：AIへの「指示（プロンプト）自体」をどう組み立てるか
- Context Engineering：AIがタスクを遂行するために「何の情報を、いつ、どこから参照すべきか」を設計する。例えば コンテキストマップ.md を用意して「まずここを見る → 必要なら次にここを見る」と案内することも、その一つ
- Harness Engineering：AIにソフトウェア開発をさせるために、コード、ドキュメント、Git、Terminal、テスト、各種Tools、SandboxなどをAIが適切に参照・操作でき、開発作業を最後まで進められるように環境・仕組み全体を整備すること
- ACI Engineering：Harnessの中でも特に、AIがFilesystem、Terminal、Git、BrowserなどのComputer機能を「どう操作するか」というAIとComputerの接点（Interface）を設計すること

ざっくり言えば、
```
Prompt Engineering
「AIにどう指示する？」
        ↓
Context Engineering
「AIに何を見せる？ どこを見に行かせる？」
        ↓
ACI Engineering
「AIにどんな手足・操作手段を与える？」
        ↓
Harness Engineering
「それら全部を組み合わせて、
 AIが実際に開発を遂行できる環境をどう作る？」
```

つまり、AIコーディングの発展は、

> 「良い指示を書く」から、「必要な情報へ導く」、さらに「AI自身がツールを使いながら開発を遂行できる環境を作る」へと、設計対象が広がってきた

と捉えると分かりやすい。

## Context Engineering観点（何をどのようにINPUTするか）
× 全てのコンテキストを渡す<br>
**○ 必要なコンテキストのみ渡すようにする**

✅特に大規模なコードベースでは、AIに全部読ませるのではなく「**必要な情報がどこにあるかをAIが迷わず発見できるようにすること**」が重要です。

↓コンテキストに該当するものはたくさんあるが、**最初から全てのコンテキストをフラットに探しに行かせない**👉
```
- 既存ソースコード
  - 実装コード
  - 型定義
  - テストコード
  - DBスキーマ / Migration
  - 設定ファイル（package.json、pyproject.toml、ESLintなど）
- ドキュメント
  - コーディング規約
  - アーキテクチャ方針
  - 仕様・要件ドキュメント
  - API仕様（OpenAPIなど）
  - README / セットアップ手順
  - ADR（過去の設計判断）
- Git / 開発履歴
  - Commit履歴
  - Git diff
  - Pull Request
  - Issue
  - Code Reviewのコメント
- 実行結果
  - Test結果
  - Build結果
  - Compiler / Linterのエラー
  - Stack Trace
  - Application Log
- 実行環境・外部情報
  - 環境変数
  - Runtime / OS / Docker環境
  - Library / Frameworkのドキュメント
  - 外部APIのドキュメント
- ユーザー / AIとのやり取り
  - 現在の依頼・Prompt
  - 過去の会話
  - AIがそれまでに調査した内容
  - AIがそれまでに行った変更・Tool実行結果
```

### 入口用ドキュメント（AGENTS.md）を作成する
- **段階的に情報を辿らせるような設計**をすればいい。
- そのHOWとして「**情報の地図であるAGENTS.md**」を作成して、まずはこれを読ませにいく。

### 既存プロダクトへ途中からAI Codingを導入するケース
- 「既存コードそのものを規約の一次情報として使う」という方針は有力
- 既存実装から推測させるものと明文化すべきものを分けるのがポイント

例えば以下は、わざわざ大量に文章化する費用対効果が低い。
```
・変数・関数の命名傾向
・class / functionの書き方
・importの並べ方
・エラーハンドリングの書き方
・Controller / Serviceの実装パターン
・Testの書き方
・Mockの使い方
・API Handlerの典型的な実装
```
さらに「代表実装」を指定すると強い....以下のように書く
```
▲ 既存実装を参考にしてください
○ 新しいAPIを実装する場合:
   - src/api/users/ を代表実装として参照
   - tests/api/users/ のTest Patternに従う
```


## Harness Engineering観点（OUTPUTする手順/環境を整える）

Harness Engineeringの実践例↓
```
・コーディングさせる時にJunit/Linter実行させて決定論的な品質担保をさせる
・過去の人によるレビュー指摘を元にセルフレビューさせる
```

👉**AIが一定の工程を通らざるを得ない仕組み・ワークフローを作ること**がHarnessたらしめている。

```
AIが実装
   ↓
JUnit実行
   ↓
失敗 ──→ エラーをAIに返す
   ↑             │
   └── 修正 ←────┘
   ↓
Linter実行
   ↓
違反 ──→ AIが修正
   ↓
PASS
   ↓
次の工程へ
```
