### HTTP セキュリティヘッダー未設定によるリスク

HTTP セキュリティヘッダーは、ブラウザに対して「このサイトをどのように安全に扱うべきか」を指示するための防御設定です。  
MDM アプリでは Firebase Hosting でフロントエンドを配信しているため、`frontend/firebase.json` に適切なヘッダーを設定しておかないと、ブラウザ側で防げるはずの攻撃を防げません。

特に問題になるのは、次のようなケースです。

#### 1. クリックジャッキングによる意図しない操作

クリックジャッキングとは、攻撃者が正規サイトの画面を外部サイト上に透明または見えにくい iframe として重ね、利用者に意図しないクリックをさせる攻撃です。

利用者の目には「キャンペーン応募」「動画再生」「閉じる」などの無害なボタンが見えていても、実際にはその背後に MDM アプリの画面が重ねられており、クリック位置が MDM 側の重要操作ボタンに合うよう調整されます。  
その結果、利用者は自分では別の操作をしたつもりでも、ブラウザ上では MDM アプリに対してクリック操作を行ったことになります。

`X-Frame-Options` または CSP の `frame-ancestors` が未設定の場合、MDM アプリの画面を外部サイトの `<iframe>` 内に埋め込まれる可能性があります。

MDM アプリでは、利用者が本番環境にログイン済みであれば、ブラウザは MDM 向けのセッション Cookie を自動送信します。  
そのため、攻撃者ページ上の iframe 内で実行された操作であっても、サーバー側からはログイン済み利用者本人の操作に見える可能性があります。

具体的には、以下のような操作が誘発されるリスクがあります。

- アカウント退会
- パスキー削除
- メールアドレス変更
- 組織アカウント削除
- フレンド削除
- チャットルーム設定変更

対策として、MDM アプリが外部サイトの iframe に埋め込まれないよう、`X-Frame-Options: DENY` または CSP の `frame-ancestors 'none'` / `frame-ancestors 'self'` を設定する必要があります。

#### 2. 秘密トークン付き URL の Referer 漏洩

`Referrer-Policy` が未設定の場合、ブラウザが外部サイトへ遷移したり、外部リソースを読み込んだりする際に、現在開いているページの URL を `Referer` ヘッダーとして送信することがあります。

MDM アプリには、以下のように秘密トークンをクエリ文字列に含む URL があります。

- `/user/signup/confirm?token=...`
- `/user/email-change/verify?token=...`
- `/user/password-reset/edit?token=...`

これらの画面から外部サイトへ遷移した場合、設定によっては `token=...` を含む URL が外部ドメインに送信される可能性があります。

トークンが漏洩すると、第三者が以下の操作を不正に実行できる可能性があります。

- 招待・会員登録の確定
- メールアドレス変更の確定
- パスワード再設定画面へのアクセス

そのため、`Referrer-Policy` で外部サイトへクエリ文字列を送らないよう制御する必要があります。

#### 3. XSS 発生時の被害拡大

`Content-Security-Policy` が未設定の場合、万が一 XSS が発生した際に、攻撃者のスクリプト実行をブラウザ側で制限できません。

MDM アプリでは、チャットメッセージ、ユーザー名、組織名、病院名、ラウンジ名など、利用者入力やDB由来の文字列を画面に表示します。  
React により通常のテキスト表示はエスケープされますが、将来的な実装変更、外部ライブラリ、HTML挿入処理、Markdown表示などが入ると、XSS の混入リスクはゼロではありません。

CSP がない場合、XSS が成立したときに以下のような被害へ広がりやすくなります。

- 利用者の画面上で不正APIを実行する
- 表示中のチャット内容や個人情報を外部送信する
- パスキー・アカウント設定画面へ誘導する
- 偽の再ログイン画面を表示して認証情報を盗む

CSP を設定しておくことで、外部スクリプトの読み込み先や実行条件を制限し、XSS 発生時の被害範囲を小さくできます。

#### 4. MIME Sniffing による意図しないスクリプト実行

MIME Sniffing とは、ブラウザがサーバーから返された `Content-Type` ヘッダーだけを信用せず、レスポンス本文の内容を見て「これは HTML ではないか」「これは JavaScript ではないか」とファイル種別を推測する挙動です。

本来、ブラウザは以下のような `Content-Type` をもとにレスポンスの扱いを判断します。

- `text/html`
- `application/javascript`
- `application/json`
- `text/plain`
- `image/png`

しかし、`X-Content-Type-Options: nosniff` が未設定の場合、ブラウザが内容を推測して、本来とは異なる種類のコンテンツとして扱う可能性があります。

例えば、本来はテキストや JSON として扱われるべきレスポンスに HTML や JavaScript のような内容が含まれていた場合、ブラウザがそれをスクリプトとして解釈してしまう可能性があります。  
これにより、意図しないスクリプト実行や XSS の足がかりになることがあります。

MDM アプリでは、フロントエンドの静的アセット、Service Worker、JSON、画像、APIレスポンスなど、さまざまな種類のファイルをブラウザへ返します。  
もし設定ミスや将来的な機能追加により、本来 `text/plain` や `application/json` として扱うべき内容がブラウザに推測解釈されると、攻撃コードが実行される余地が生まれます。

対策として、`X-Content-Type-Options: nosniff` を設定し、ブラウザに MIME type の推測をさせず、サーバーが指定した `Content-Type` に従わせる必要があります。

#### 5. HTTPS 強制不足による通信保護の弱体化

`Strict-Transport-Security` が未設定の場合、ブラウザに対して「このドメインは必ず HTTPS でアクセスする」と記憶させることができません。

MDM アプリはログイン Cookie、認証トークン、チャット情報、個人情報を扱うため、常に HTTPS で通信されるべきです。  
HSTS を設定することで、利用者が誤って `http://mdm-95.com` にアクセスした場合でも、ブラウザ側で HTTPS に強制できます。

#### 6. 不要なブラウザ機能の利用許可

`Permissions-Policy` が未設定の場合、カメラ、マイク、位置情報などのブラウザ機能について、サイト全体として明示的な制限をかけられません。

MDM アプリでは QR 読み取りなどでカメラを使う場面がありますが、すべての画面で広く許可されるべきではありません。  
必要な機能だけを必要な範囲に限定することで、XSS や不正な画面誘導が発生した場合の悪用余地を減らせます。

### MDM アプリでの影響まとめ

HTTP セキュリティヘッダーが未設定のままだと、MDM アプリでは特に以下のリスクがあります。

- ログイン済みユーザーに退会・削除・設定変更などを誤操作させる
- 招待、メール変更、パスワード再設定などの秘密トークンが外部に漏れる
- XSS 発生時にチャット内容や個人情報の漏洩へつながる
- 外部スクリプトや不正リソースの読み込みをブラウザ側で止められない
- ブラウザの MIME 推測により意図しないスクリプト実行が起きる
- HTTPS 強制や不要なブラウザ機能制限が効かない

そのため、Firebase Hosting の `headers` 設定で、少なくとも以下を追加する必要があります。

- `Content-Security-Policy`
- `X-Frame-Options` または CSP の `frame-ancestors`
- `Strict-Transport-Security`
- `Referrer-Policy`
- `X-Content-Type-Options`
- `Permissions-Policy`
